- 원인 — Java `Instant`의 나노초 정밀도와 DB `DATETIME(6)`의 마이크로초 정밀도가 달라, 경계 시각 비교가 어긋났다.
- 해결 — 완료 시각을 DB 정밀도인 마이크로초 단위로 저장하도록 맞췄다.

## 2026-11-25 — 완료된 동승방 삭제 방식 변경 후 기존 테스트 실패

- 상황 — P1 동승 이력을 구현하면서 완료된 방을 방장이나 참가자가 **각자 자신의 목록에서만** 삭제하도록 요구가 바뀌었다. 이전 구현은 방장이 완료 방을 삭제하면 방 상태를 `CANCELLED`로 변경해 모든 사람의 목록에서 숨겼다.
- 실패 증상 — `RideFlowIntegrationTest.onlyHostCanDeleteCompletedRoomAndSettlementRecordRemains`는 삭제 후 방 상태가 `CANCELLED`일 것으로 기대했지만, 새 구현에서는 `COMPLETED`로 남아 `expected: CANCELLED but was: COMPLETED`로 실패했다. 이는 새 코드의 방 상태가 틀렸다는 뜻이 아니라 테스트가 **이전 요구**를 검사하고 있다는 신호였다.
- 원인 확인 — 방 상태 하나로 모든 사용자의 표시 여부를 결정하는 구조에서는 한 사람의 삭제와 다른 동승자의 기록 보존을 동시에 표현할 수 없었다. `room_completions`와 정산 데이터는 방 전체에 속하고, 개인별 목록에서 숨길지는 사용자마다 달라야 했다.
- 해결 — `ride_history_hides`에 `(room_id, user_id)`별 숨김 기록을 두고 완료된 방의 수동 삭제는 해당 사용자에게만 적용했다. 모집 중 방의 기존 전체 취소 동작은 유지했다. 7일 경과 시 방은 일반 목록에서 보관 처리하지만 실제 동승자의 이력 조회는 `room_completions`와 참여 권한을 기준으로 허용했다. 테스트도 방장 삭제 후 참가자 이력 유지, 참가자의 독립 삭제, 비동승자 접근 거절, 7일 뒤 정산 조회를 검사하도록 고쳤다.
- 확인 — 변경된 방 흐름 통합 테스트 25개가 통과했다. 실제 휴대폰에서 두 계정의 목록이 독립적으로 보이는지는 아직 확인하지 않았다.
- 면접에서 설명할 핵심 — “완료 방의 상태를 `CANCELLED`로 바꾸는 방식은 방장 한 사람의 삭제를 모든 동승자의 삭제로 확장하는 모델링 오류였습니다. 방의 완료 기록과 사용자별 숨김 상태를 분리했고, 권한과 7일 보관 경계를 통합 테스트로 확인했습니다.”

## 2026-11-25 — 새 숨김 테이블 추가 후 테스트 데이터 정리 실패

- 실패 증상 — 첫 백엔드 전체 검사에서 `ride_history_hides`의 `room_id` 외래 키 때문에 `taxi_rooms` 삭제 시 참조 무결성 오류가 났다. 한 테스트가 숨김 기록을 만든 뒤 다음 테스트의 초기화 단계가 방을 먼저 삭제하려 했다.
- 원인 확인 — 기존 `RideFlowIntegrationTest.cleanup()`은 완료 시각·정산·참여 기록만 먼저 지웠고, 새 자식 테이블인 `ride_history_hides`를 정리하지 않았다. 운영 기능의 조회 실패가 아니라 테스트 데이터 삭제 순서 문제였다.
- 해결 — 테스트 정리 순서에서 개인별 숨김 기록을 방보다 먼저 삭제하도록 추가했다. DB의 외래 키 제약은 유지해 실제 데이터 관계가 깨지지 않도록 했다.
- 확인 — 수정 후 방 흐름 테스트 25개와 전체 백엔드 테스트가 통과했다.
- 면접에서 설명할 핵심 — “새 테이블의 외래 키를 유지한 채 테스트 정리 순서를 고쳤습니다. 제약을 없애는 대신 자식 레코드부터 정리해 테스트 간 데이터 간섭을 해결했습니다.”

## 2026-11-25 — 채팅 화면의 타입·React 린트 오류

- 실패 증상 — `npm run typecheck`에서 채팅 조회의 `messageCursor.current`와 이전 메시지 상태가 `null`일 수 있다는 오류가 났다. 이어 `npm run lint`에서 화면을 그리는 도중 `ref.current`를 읽는 코드가 `react-hooks/refs` 규칙에 걸렸다.
- 원인 확인 — 메시지 조회가 비동기로 끝나는 사이 채팅방이 바뀌거나 화면이 닫히면 참조값이 사라질 수 있다. 또 `ref`는 렌더링을 일으키지 않으므로 로딩 안내처럼 화면에 표시할 값을 `ref.current`에서 직접 계산하면 화면 갱신 시점을 보장하기 어렵다.
- 해결 — 조회 응답을 반영하기 전에 현재 방 ID와 참조값의 존재를 확인하고, 이전 메시지 상태가 없을 때는 빈 목록으로 처리했다. ‘불러오는 중/메시지 없음’ 표시는 렌더링용 상태인 `messageSnapshot`으로 계산하도록 변경했다.
- 확인 — 수정 후 TypeScript 검사와 Expo 린트가 모두 통과했다. 휴대폰에서 채팅방 전환·재진입 화면은 아직 확인하지 않았다.
- 면접에서 설명할 핵심 — “비동기 응답은 화면이 다른 방으로 바뀐 뒤 돌아올 수 있으므로 방 ID를 확인한 뒤 적용했습니다. UI에 필요한 값은 `ref`가 아니라 React 상태에서 계산해 렌더링 규칙을 지켰습니다.”

## 2026-11-25 — 채팅 증분 조회 테스트의 메시지 ID 가정 오류

- 실패 증상 — 새 채팅 통합 테스트에서 `GET /messages?after=1`의 결과를 1개로 예상했지만 2개가 반환됐다. 출력은 `JSON path "$.data.length()" expected:<1> but was:<2>`였다.
- 원인 확인 — 테스트가 첫 메시지의 ID를 `1`로 고정했다. DB 자동 증가 ID는 이전 테스트 실행이나 다른 방의 메시지 생성에 따라 커질 수 있으므로, 이 테스트에서 만든 첫 메시지가 반드시 ID 1인 것은 아니다. API의 `after` 조건 자체가 잘못됐다는 근거는 없었다.
- 해결 — 테스트에서 실제 저장된 첫 메시지 ID를 조회해 `after` 값으로 사용했다. 검증 목표는 특정 숫자가 아니라 ‘이미 본 메시지 이후의 새 메시지만 받는다’는 동작으로 유지했다.
- 확인 — 채팅 통합 테스트 2개와 전체 백엔드 테스트 34개가 통과했다. 승인된 동승자 송수신, 대기자·외부인 차단, 승인 취소 후 접근 차단, 본문 길이·CSRF, 방별 기록 분리를 자동 검사했다.
- 면접에서 설명할 핵심 — “자동 증가 키를 1로 가정해 테스트가 실행 환경에 의존했습니다. 저장된 식별자를 기준으로 증분 조회를 검증하도록 바꿔 테스트의 재현성을 높였습니다.”
